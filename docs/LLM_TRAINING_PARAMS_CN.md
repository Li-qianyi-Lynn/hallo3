# LLM 训练参数通俗解释

> 基于 Hallo3 项目代码，面向 LLM 小白的训练参数说明。

---

## 用做饭来理解训练参数

把训练想象成做一桌菜：你有 **1000 道菜谱**（训练数据），需要让模型（厨师）把所有菜都学会。

---

## 核心参数

### Batch Size — 一次端多少盘

厨师学菜的时候，可以：
- 一次看 **1 道菜** 学一次 → batch size = 1
- 一次看 **8 道菜** 学一次 → batch size = 8

**batch size 越大**，学一次看的例子越多，方向更稳，但需要更大的桌子（显存）。

> Hallo3 里 `train_micro_batch_size_per_gpu = 1`，因为**视频太大了**，一张 A100 一次只装得下 1 个视频。

---

### Iteration（iter）— 学了多少次

每看一批菜、更新一次记忆 = **1 个 iter（step）**。

```
iter 1:     看第1批 → 更新记忆
iter 2:     看第2批 → 更新记忆
...
iter 30000: 训练结束
```

> Hallo3 设置 `train_iters = 30000`，也就是**更新 3 万次权重**。

---

### Epoch — 把所有菜都过了一遍

1 个 epoch = 把 1000 道菜全看了一遍。

| | Epoch | Iter |
|---|---|---|
| 粒度 | 粗（大轮次） | 细（每次更新） |
| 关系 | 1 epoch = 数据量 ÷ batch_size 个 iter | — |

> Hallo3 **不用 epoch**，因为视频数据是流式的，数据量不固定，直接指定 iter 数更方便。

---

### Gradient Accumulation — 小碗拼成大碗

显存不够用，batch size 只能设 1，但想要 batch=8 的效果怎么办？

**分 8 次看，先别更新记忆，把感受攒着，攒够 8 次再一起更新。**

```
看第1个视频 → 攒着
看第2个视频 → 攒着
...
看第8个视频 → 一起更新！
```

> `gradient_accumulation_steps`：省显存，但慢一些。
>
> **effective batch size** = `每卡batch × 卡数 × 梯度累积步数`
> 
> 例：Hallo3 在 8 卡 A100 上 → 1 × 8 × 1 = **8**

---

### Learning Rate（lr）— 每次学多少

学了一道新菜，要改变多少原来的记忆？

| lr 大小 | 效果 |
|---|---|
| 太大 | 学太猛，忘了之前学的（发散） |
| 太小 | 几乎不学（不收敛） |
| 刚好 | 稳定收敛 |

> Hallo3 用 `lr = 1e-5`（0.00001），因为是**在已有大模型上微调**，要小心翼翼地调，不能改太多。

---

### Gradient Clipping — 给学习速度踩刹车

有时候某一步梯度特别大（比如遇到了奇怪的样本），如果不管，模型会**突然乱跑**。

> `gradient_clipping = 0.1`：不管梯度多大，最多只走 0.1 这么远。
> 就像车速限制，防止出事故。

---

### Checkpoint Activations（Gradient Checkpointing）— 省内存的代价

训练时，每一层的"中间计算结果"需要存下来用于反向传播。

| 模式 | 内存 | 速度 |
|---|---|---|
| 不开 | 全存，占用大 | 快 |
| 开了（Hallo3 开了） | 省约 50% | 慢约 30% |

> 相当于：做菜时不记笔记，需要复盘时再重做一遍。

---

### ZeRO Stage 2 — 多人分担记忆

8 张 GPU 一起训练时，优化器的状态（记录每个参数的历史更新量）非常占内存。

ZeRO-2 的做法：**8 张卡每张只记 1/8 的状态**，需要时互相通信。

> 就像 8 个厨师共用一本菜谱笔记本，每人只负责保管某几页。

| ZeRO Stage | 分片内容 | 省内存程度 |
|---|---|---|
| Stage 1 | 优化器状态 | 少 |
| Stage 2 | 优化器状态 + 梯度 | 中（Hallo3 使用） |
| Stage 3 | 优化器状态 + 梯度 + 模型参数 | 最多 |

---

### BF16 — 用"草稿本"代替"正式本"

| 精度 | 每个数占空间 | 特点 |
|---|---|---|
| FP32（全精度） | 4 字节 | 精确，慢 |
| BF16（半精度） | 2 字节 | 稍粗糙，省一半显存，快约 2 倍 |

> Hallo3 用 BF16 训练，FP32 保存最终权重。
> 就像草稿用铅笔（快），定稿用钢笔（准）。

---

### num_workers — 备料的助手数量

数据加载（读视频文件）和 GPU 计算是并行的。

> `num_workers = 8`：安排 **8 个工人** 提前把下一批视频读好，GPU 不用等待。

---

## 优化器参数

| 参数 | Hallo3 值 | 含义 |
|---|---|---|
| `lr` | 1e-5 | 学习率 |
| `weight_decay` | 1e-4 | L2 正则化，防止过拟合 |
| `betas` | [0.9, 0.95] | Adam 动量系数（历史梯度的"记忆衰减率"） |
| `eps` | 1e-8 | 数值稳定项，防止除以零 |
| optimizer | FusedEmaAdam | 带 EMA 的 Adam，训练更稳定 |

---

## 视频数据参数

| 参数 | Hallo3 值 | 含义 |
|---|---|---|
| `max_num_frames` | 49 | 每个样本取多少帧（约 6 秒 @ 8fps） |
| `fps` | 8 | 训练时视频的采样帧率 |
| `video_size` | [480, 720] | 帧分辨率 H×W |
| `skip_frms_num` | 3 | 跳过视频首尾各 3 帧，避免场景切换噪声 |
| `frame_interval` | 1 | 每隔 N 帧取一帧（=1 表示连续取帧） |
| `audio_margin` | 2 | 每帧音频上下文窗口 [-2,-1,0,+1,+2]，共 5 帧 |

---

## 整体训练流程

```
数据集（视频文件）
    ↓
[num_workers=8 个工人提前备料]
    ↓
每次取 1 个视频（batch_size=1）
    ↓
[重复 gradient_accumulation 次，攒梯度]
    ↓
[gradient_clipping 踩刹车，防止梯度爆炸]
    ↓
用 lr=1e-5 更新模型权重（BF16 精度）
    ↓
重复 30000 次（train_iters）
    ↓ 每 500 步保存一次 checkpoint
训练完成
```

## Hallo3 两阶段训练

| | Stage 1 | Stage 2 |
|---|---|---|
| 数据集类 | `SFTDataset` | `Stage2_SFTDataset` |
| 输入模态 | 视频 + 参考图 + 人脸 embedding | Stage 1 基础上 + **音频 embedding** |
| 加载权重 | 预训练 CogVideoX-5B | Stage 1 训练后的 checkpoint |
| 训练目标 | 学习人脸外观控制 | 学习音频驱动口型 |
| train_iters | 30000 | 30000 |

## 面试高频追问

**Q: batch size 和 effective batch size 有什么区别？**

> 显卡显示的 batch size 是每张卡实际处理的数量，effective batch size 才是模型"感知"到的批次大小：
>
> `effective batch size = 每卡batch × 卡数 × 梯度累积步数`
>
> Hallo3：1 × 8卡 × 1 = **8**

**Q: iter 和 epoch 哪个更常用？**

> 大模型训练通常用 iter，因为数据集太大，一个 epoch 可能要跑几周，且流式数据没有明确的 epoch 边界。小任务（分类、NLP fine-tune）更常用 epoch。

**Q: 为什么 fine-tune 的 lr 要比预训练小？**

> 预训练是从零开始，可以大步走。Fine-tune 是在已经很好的模型上微调，步子太大会"破坏"原来学到的知识（灾难性遗忘），所以要小步调整。

**Q: gradient checkpointing 有什么代价？**

> 省约 50% 显存，但反向传播时需要重新计算前向的中间值，速度慢约 30%。显存紧张时值得开。

**Q: ZeRO 和 Data Parallel 有什么区别？**

> 普通 Data Parallel 每张卡都保存完整的模型 + 优化器状态，内存浪费大。ZeRO 把这些状态分片到各卡，每张卡只存一部分，合起来才是完整的，大幅节省显存。
